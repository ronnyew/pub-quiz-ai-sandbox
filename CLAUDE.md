# Project Constitution & Engineering Rules

## Architecture & Guardrails
- Stack: Node.js + Express, hosted on Google Cloud Run, database on Firestore. Root `firestore.indexes.json` (wired via `firebase.json`) defines required composite indexes; `.github/workflows/deploy.yml` runs `firebase deploy --only firestore:indexes` on main after `google-github-actions/auth`. The deploy service account (`github-deployer@pub-quiz-ai-sandbox.iam.gserviceaccount.com`) must have `roles/datastore.indexAdmin` or `roles/firebase.admin`.
- Player frontend: Tailwind CSS only, plus `public/styles/neon-tokyo.css` extracted from `design/player/*/code.html` (`.cyber-grid`, `.neon-glow-pink`, `.neon-glow-cyan`, Stitch color tokens, `Sora`, `Space Grotesk`, `Inter`). Do not add DaisyUI to the Neon Tokyo player UI.
- Cost Control: Never introduce background polling loops or persistent WebSockets that prevent Cloud Run from scaling to zero.
- **Bounded & Paginated Backend Queries:** All list/history functions must query the active datastore (Firestore when `shouldUseFirestore()` is true, and local/memory stores otherwise) using indexed filters and explicit `.limit()` pagination—never relying on RAM-only Maps in production or scanning entire collections unbounded.
- **Precompute & Cache End-of-Game Summaries (Zero N+1 Secret Reads):** Compute final player ranks, totals, and accuracy/correct counts once atomically when a game transitions to `COMPLETED` and store them on the public `game_rooms/{pin}` document (`playerSummaries`). Dashboard and list views must render from those cached public fields—never reading `game_room_secrets` or recomputing full breakdowns per history row.
- Security: Never hardcode API keys or credentials. Validate and sanitize all user inputs before database writes or LLM calls.
- **Anti-cheat option keys:** Never derive `correctAnswerId` or correct option indices sequentially or deterministically from public `questionId` strings. Author explicit option placements in seed data (or other non-leaking metadata). When building a game deck, always shuffle each question’s option presentation order with an injectable RNG and remap `correctAnswerId` to the shuffled option id.
- **Content separation:** Never hardcode legal copy, footer links, or static marketing/UI strings inside HTML templates (`lib/player-layout.js`, `lib/player-pages.js`, `index.js`, or similar). Store all such copy in `content/site-content.json` and read it only through `lib/content-store.js` (the abstraction future Admin Portal can swap to Firestore without changing routes or templates). All Markdown rendered for pages MUST pass through `lib/content-store.js` and `sanitize-html` before injection into templates.
- **No regex HTML rewriting:** Never use regular expressions to parse or rewrite HTML strings after `sanitize-html` (nested `<ul>` / `<li>` trees break easily). Apply CMS Markdown styling only via `sanitize-html` `transformTags` and CSS selectors (e.g. `.content-markdown ul`).
- **URL & slug validation:** All CMS/user-defined `footer_links[].path` values MUST match `/^[a-z0-9]+(?:-[a-z0-9]+)*$/` and MUST NOT use reserved slugs (`admin`, `api`, `health`, `dashboard`). Validate in `lib/content-store.js` before routes or `href="/${slug}"` rendering. Sanitized Markdown links MUST block `javascript:` / `data:` schemes (via `sanitize-html`), strip protocol-relative URLs (`//...`), allow only `http://`, `https://`, `mailto:`, or single-slash internal paths (`/…` not `//…`), and MUST strip author-supplied `class` values in `transformTags` before applying typography—never merge CMS classes with Neon Tokyo classes.
- **Slice 4 lobby chrome:** On **Start a Game** (`GET /game/:gamePin`) and **Play a Game** waiting views, the shared header shows only the `PUB QUIZ` wordmark—do not repeat Game PIN or player count there. Hero badges carry Game PIN / player headcount. The host lobby **PLAYER GRID** in the right column (under launch, above nothing) is an intentional product extension beyond the Stitch export and must not be removed in later slices without an explicit PRD change.
- **Slice 4 dashboard chrome:** `GET /dashboard` follows `design/player/dashboard_with_match_modal/code.html` for hero, action cards, and match history/modal styling (`public/styles/neon-tokyo.css`). The hero **SIGN OUT** button (`POST /api/auth/signout`, `.pq-dashboard-signout`, `cursor: pointer`) is an intentional product requirement beyond the Stitch mockup and must not be removed in future slices or `/evaluate-slice` checks. The hero’s top-left **cyan corner bracket** (matching the Stitch export) is required; the rotated pink square accent from the mock is intentionally omitted so it never collides with SIGN OUT.
- **Slice 4 routes & invites:** Player flows use `/game/:gamePin`, **Game PIN** copy, and invite URLs `${APP_BASE_URL || requestOrigin || https://pubquiz.app}/join?game={pin}` (`GET /join` accepts legacy `?room=`). `POST /game` (not `GET /game`) creates `game_rooms` and redirects `303` to the lobby. Back-compat API aliases `POST /api/rooms` and `GET /api/rooms/:pin` delegate to the same handlers as `/api/games`.
- **Scoring:** Correct on-time answers add `basePoints`; wrong on-time answers subtract `basePoints`; unanswered or post-`closesAt` submissions award 0. Room totals may be negative.
- **Slice 5 deck & HUD:** `buildDeck` pools all questions from selected packs, shuffles, slices `questionCount`, and shuffles each question’s options (no topic/question difficulty ratings). Default launch deals every question in the selected packs (sum of pack pools, max 100). Launch uses `runGameRoomLaunchTransaction` so public `dealQuestions` and `game_room_secrets` are written atomically while `status === WAITING'`, merging the latest `players` and fresh `scores` from the transactional read so late lobby joiners are not dropped. Gameplay HUD is minimalist (no topic pill, tags, `+N PTS`, or between-question explanations); play APIs withhold grading while `roundPhase === OPEN'` and may expose `correctAnswerId`, `isCorrect`, `pointsAwarded`, and `scores` in `REVEAL` without `explanation`. Only the host may `POST …/advance`.
- **Slice 6 results & breakdown:** `GET /rooms/:pin/results` (FR-10 podium) ranks by score then average latency then `userId`; each row shows correct count and average speed only (not XP or streak labels). The signed-in player’s row links to `GET /rooms/:pin/breakdown?user=`. `GET /dashboard` lists real matches from `listGameRoomsForUser`; rows open a Tailwind match breakdown modal fed by `GET /api/games/:pin/breakdown` (5 rows per page). Standalone breakdown URL documents the same drawer. Verified answers (`correctAnswerId`, `explanation`, `sourceCitations`) appear only when `status === COMPLETED`. `RETURN HOME →` on results links to `/dashboard`.

## Spec & Roadmap Synchronization
When an intentional product refinement supersedes an older requirement (for example `/game` routes and **Game PIN** copy replacing `/rooms` and **Room PIN**, `APP_BASE_URL`-driven `/join?game=` invite URLs replacing hardcoded `https://pubquiz.app/join?room=`, host lobby **PLAYER GRID**, or dashboard hero **SIGN OUT**), the Builder **must update the matching roadmap done-checks, FR entries in `specs/prd-neon-tokyo.md`, and this file in the same slice** so no stale requirement remains. Builder and Evaluator both treat the updated spec as source of truth.

## Workflow & Accountability
- Never suggest pushing directly to `main`. All changes must be structured for a Pull Request.
- Every new API route or game logic function must include a corresponding unit test.
- DOCUMENTATION RULE: Before concluding any coding task, append a concise entry to `ENGINEERING_LOG.md` in this repo summarizing: (1) What changed, (2) Why it was designed that way, and (3) Any security or cost implications.
